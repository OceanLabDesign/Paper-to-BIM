# 0003. 15 類偵測類別與「順序即 id」

## 脈絡

規格 §4 只給了三件事：15 類、順序即 id、永不重排。**沒有給清單。**
清單同時是 `03_detections`／`03_elements` 的 `class_name` 值、
plan `judgments[].type` 的唯一合法來源、以及 §6.2 規則 1 的檢查依據。

限制：一旦有資料引用，順序就鎖死 —— 這是全專案最不可逆的一個決定。
1979 年台灣建照圖是曬圖，有摺痕與陰影；`MIT_LINE_LENGTH = 60px` 這個門檻
會直接決定某些類別是否根本偵測不到。

## 選項

清單本身有無限多種寫法，所以改成從**四個互不相容的視角**各提一版：
結構與構造／製圖慣例／偵測器可行性／下游消費者。
再由三位評審（規格符合度／永久性／1979 圖面現實）各自評分。

四版分數 78 / 78 / 77 / 76 —— **極接近，代表沒有哪個視角壓倒性正確**。

## 決定

以結構版為骨幹綜合，排序依**下游依賴深度**：

```
0–1   wall, column                    §3 唯二有落地產出的類（07_walls/07_columns）
2–3   dim_line, dim_text              §6.2 規則 3 下唯一合法的座標來源
4–6   opening, door, window           牆的二階幾何
7–9   stair, level_line, level_text   供給 z；level_* 是脫離 ASSUMED 與 _draft 的唯一路徑
10–12 room_label, hatch, material_note 證據級
13–14 element_tag, fixture            v1 無下游消費者，最可能被拆細
```

## 後果

- 排除了 `grid_line`、`slab`、`beam`、`north_arrow`、萬用桶 `unknown` 等 16 項，
  **理由完整留在 `core/classes.py` 的 `EXCLUDED`** —— 日後有人想 append 時先看那裡
- **放棄了「事後插隊」的可能。** 新類別只能 append 到 id 15 起
- `unknown` / `other` 這種萬用桶被明確拒絕：catch-all 是 `classes.py` 的合法成員，
  會讓 §6.2 規則 1 永遠攔不下不確定的東西，正是 §1「不確定往上傳不往下傳」的反面
- 重新考慮的時機：**現在**（尚無資料引用，改是免費的）。一旦跑過真實案件就不行了

## 依據

規格 §4、§6.2、§8、§12；`core/config.py` 的實測像素尺度；
2026-08-22 的四視角提案與三評審評分（8 個 agent）。
