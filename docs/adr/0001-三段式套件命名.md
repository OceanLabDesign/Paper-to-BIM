# 0001. 三段式套件命名與中樞的函式名

## 脈絡

規格用的是比喻：視神經、中樞、手。骨架照著取了 `passive/` `brain/` `hands/`。
repo 要放上公開 GitHub 後，這組名字對外讀起來是內部黑話。

限制：`brain/` 與 `core/` 是規格 §5、§4 明文寫的路徑；
`brain()` 這個函式名出現在 §5 **逐字轉錄**的迴圈骨架裡
（`plan = brain(case_dir, version=n, residuals=prev)`）。

## 選項

| 選項 | 好處 | 代價 |
|---|---|---|
| perception / planning / execution（採用） | 自駕與機器人領域的通用架構詞；`planning` 名實相符 —— 中樞的產出字面上就是 plan | 要動 §5 的逐字 code block |
| interpret / draft | `draft` 有製圖語感 | `draft/` 與裁決 §6 的 `_draft` 後綴撞義（該後綴代表「粗胚、不可信」）；`interpret` 與 s02 版面判讀語意重疊 |
| 維持 brain / hands | §5 一字不動 | 公開 repo 裡的比喻性命名 |

函式名另有一組：`agents()`、`propose_plan()`、`plan()`。
`plan()` 直接出局 —— `plan = plan(...)` 在第二輪迴圈會被區域變數遮蔽。

## 決定

`perception/` → `planning/` → `execution/`，函式 `brain()` → `propose_plan()`
（模組 `proposer.py` / `fake_proposer.py`）。英文 `brain` 一詞退出 repo，
概念一律用規格本來的詞「中樞」。

不選 `agents()` 的決定性理由：它是複數，但中樞只有一個 —— 真正複數的 agent 是
`planning/subagents/` 那兩支。而且 §12 的核心主張是**迴圈控制權不准交給 agent**，
在唯一那個 LLM 呼叫點冠上 agent 名是把重點指反了。§7.3 戒律開宗明義
「你的產出是一份繪圖計畫，不是動作」—— 函式名該講產出。

## 後果

- 中文比喻退到 docstring 與規格，套件層對外是通用架構詞
- **放棄了 §5 code block 的逐字轉錄。** 裁決文件已明示「§5 是鐵則指控制權在程式碼，
  不是這段一字不能改」，改完同步更新了文件
- 重新考慮的時機：若日後真的出現多個平行中樞，`agents()` 的命名空間才有意義

## 依據

規格 §5、§7.3、§12；《待決事項 — 裁決》對套件命名的回應；2026-08-22 對話裁決。
