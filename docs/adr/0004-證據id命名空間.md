# 0004. 證據 id 命名空間 `EVIDENCE_NS`

## 脈絡

§6.2 規則 2：「任一 judgment 的 evidence 為空，或**引用的 id 不存在於 CSV**」即退件（rejection）。
§13 派工單再強調一次：「規則 2、3 要**實際去 CSV 查 id 存在性**」。

但 plan 裡的證據寫成 `命名空間#id`（§6.1 範例：`pair#12`、`chain#c003`、
`det#x0101`、`read#p02_d0038`、`quality#q13`），而規格**沒有任何一處說明前綴
對應到哪個 CSV 的哪個欄**。沒有這張表，規則 2 在物理上無從實作。

## 選項

| 選項 | 好處 | 代價 |
|---|---|---|
| 放進 `core/fields.py` 當契約（採用） | 與欄位定義同一個地方，改一次；smoke 查得到 | 契約（contract）多一個代擬項 |
| 硬編在 `validate.py` 裡 | 不動契約 | 加新 CSV 時要改兩處，而且忘了不會有人發現 |
| 不做，規則 2 降級成查格式 | 最省事 | **直接違反 §13 明文**，而且驗收（validation）閘門（gate）形同虛設 |

第三個選項是真實風險：§13 自測（self-test）若拿 §6.1 的格式範例（id 是假的）當通過性測資（test data），
測試必然紅，而最省事的「修法」就是把規則 2 降級 —— 這條路已在
`planning/validate.py` 的 docstring 明文擋掉。

## 決定

放進 `core/fields.py`：`EVIDENCE_NS = {前綴: (case.FILES 短名, id 欄名)}`，
另加 `ID_COLUMN` 給 validate 查表用。前綴字面取自 §6.1 範例，對應關係為代擬。

## 後果

- 規則 2 變得可實作，而且 `tests/smoke.py` 的 `[4]` 會檢查每個前綴都指得到
  實際存在的檔與欄、`[6]` 會拿最小測資實際解析一次
- **放棄了「契約只放規格明文寫過的東西」**這條潔癖 —— 但不放就寫不出 validate
- 重新考慮的時機：規格若補上官方的命名空間（namespace）定義，以那份為準並標記本 ADR 為 superseded

## 依據

規格 §6.1、§6.2 規則 2、§13；`core/fields.py`、`tests/smoke.py` [4][6]。
