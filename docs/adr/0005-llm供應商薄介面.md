# 0005. LLM 供應商用自寫薄介面，不用統一層套件

## 脈絡

需求：`planning/` 要能搭配各家 AI 的 API、也要能用本地多模態 LLM，
並且要能使用工具。

限制：這個專案的既有調性是「先寫腳本不寫系統」、「一開始不上資料庫、
不做網頁校對（review）、不追求全自動」，而且目前**零第三方相依**。
中樞（planning）的實際需求很窄：單輪、同步、帶工具、帶圖 —— 迴圈控制權（control of the loop）在 §5 的
orchestrator，不在 LLM 層。

## 選項

| 選項 | 好處 | 代價 |
|---|---|---|
| 自寫薄介面（thin interface）＋兩個轉接器（採用） | 零新相依；介面剛好對齊真實需求 | 新廠商若不相容要自己寫轉接器（adapter） |
| LiteLLM 之類統一層（unified LLM API layer） | 一個相依換掉數十家；工具呼叫格式差異由它正規化 | 多一個相依、它的抽象會滲進來、除錯多一層 |
| 只做 Anthropic | 最少程式碼 | 本地多模態要等下一輪，不符合需求 |

## 決定

自寫 `planning/llm/base.py` 的 `Provider` 介面，兩個轉接器：
`anthropic`（原生）與 `openai_compat`。

決定性理由：**`openai_compat` 一支就涵蓋 OpenAI、Ollama、vLLM、LM Studio、
llama.cpp server**，因為它們都提供 `/v1/chat/completions` 相容端點 ——
「各家 API」與「本地多模態」這兩個需求被同一支轉接器同時滿足，
統一層套件能多買到的覆蓋率（coverage）因此小得多。

## 後果

- 相依維持零；金鑰走環境變數，不進 `core/config.py`（那支會進版控）
- 本地部署順帶解決一件事：掃描圖含個資（personal data）與著作權，**跑本地模型時圖不出機器**
- 工具規格（tool spec）集中在 `planning/tools.py` 的 `TOOL_SPECS`，一份宣告餵所有供應商（provider），
  由轉接器轉成各廠商格式；smoke `[7]` 會查它與函式雙向對得上
- **放棄了「換廠商完全不用寫程式」**。新增不相容的廠商＝寫一支轉接器
- 重新考慮的時機：若要同時支援超過四五家不相容的廠商，統一層才划算

## 依據

規格 §1、§5、§7.2；2026-08-22 對話裁決（使用者在三個選項中選了薄介面）。
