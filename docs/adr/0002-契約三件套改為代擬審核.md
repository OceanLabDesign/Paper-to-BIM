# 0002. 契約三件套改為「代擬＋審核」

## 脈絡

規格 §4 原文：「契約三件套 —— 負責人親手寫，Claude Code 只能引用」。
§11 建造順序第 1 步就是它。

實際狀況：三個檔空著，而 `fields`／`classes`／`plan_schema` 是所有下游模組的
import 目標 —— **整個專案卡在第 1 步**，連 validate 都寫不了。

## 選項

| 選項 | 好處 | 代價 |
|---|---|---|
| 代擬＋審核（採用） | 解除阻塞，負責人審核成本遠低於從零寫 | 草案有被當定版的風險 |
| 等負責人親手寫 | 完全照規格 | 專案停擺 |
| 直接定版 | 最快 | 違反 §4，而且 `classes.py` 的順序一旦有資料引用就鎖死 |

## 決定

改為代擬＋審核。每一項標明【定版】（規格或裁決已寫死，照抄）或【草案】（代擬），
且**未經負責人確認前不得產生任何正式資料**。

風險用兩道機制擋：檔頭的顯著標記，以及 `tests/smoke.py` 的 `[3]` 會用 AST 判斷
三個檔到底寫了沒（只有 import 不算）。

## 後果

- §11 第 1 步解除，validate 與各模組可以開工
- **放棄了「契約只由一個人執筆」的單一心智模型**，換來的是每項都要標來源
- 重新考慮的時機：負責人逐條審完並拿掉【草案】標記後，本 ADR 的風險段即失效

## 依據

規格 §4、§11；2026-08-22 對話中負責人指派「你幫我處理」。
